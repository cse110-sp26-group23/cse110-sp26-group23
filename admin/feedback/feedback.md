# Team 24 Code Review
*By Team 23*

## Strengths: What the team is doing well
One thing we really like about Team 24’s project is that the idea feels clear and fun right away. The game, Phantom Type, has a haunted roguelite theme where players type real code lines to defeat ghost enemies. We think this is a strong direction because the gameplay connects well with the learning goal: instead of typing random words, the player is practicing real programming syntax in JavaScript, HTML, or CSS. Their README is also very organized. It explains the live demo, project goal, file structure, tech stack, testing setup, and architecture clearly, which makes it easy for another team to understand how the project is built. We also liked that they separated the code into folders like engine/, ui/, audio/, data/, snippets/, and utils/, because this makes the project easier to maintain and divide between teammates.

## Improvements: Concrete suggestions for what could be improved
One improvement we would suggest is to make the current progress clearer in the README or MVP file. Right now, the README describes a lot of features, such as boss encounters, upgrade selection, horror effects, and end-of-run stats, but some related GitHub issues are still open, including the boss system, upgrade system, upgrade selection screen, visual theme, and enemy defeat animation. Because of that, it is a little hard as a reviewer to tell what is already fully working versus what is planned or still in progress. A practical fix would be to add a small checklist near the top of the README, like: “Working now,” “Partially implemented,” and “Still in progress.” For example, they could mark language selection and snippet typing as working, but mark boss typing loop or upgrade card selection as in progress if those are not fully connected yet. This would make the project status much easier to understand before the final demo. 
Another improvement is to polish the user experience around the educational part of the game. The MVP says the game is meant for beginner-to-intermediate CS students and that typing real code should reinforce syntax and function structure. That is a good goal, but the game could make that learning value more visible. For example, after a wave, they could show the full function the player just typed and add a short sentence explaining what it does, like “This function loops through an array and returns the largest value.” Even a simple explanation panel would make the project feel more educational, not just like a themed typing game. They could also highlight mistakes by type, such as missing brackets, wrong capitalization, or forgotten semicolons, so players understand what syntax errors they are making most often.
Another improvement is regarding the testing setup. When we ran the tests, 4 suites passed and 2 test suites failed, with 71 passed tests, and 22 failed tests. This is a minor issue, as the game is obviously still in heavy development, but the codebase should likely accurately pass tests. Another addition could be writing tests, after further development that test how different components interact with each other. 

## Question: A thoughtful question about design, implementation, or direction
How much do you want the game to prioritize learning compared to speed and survival? For example, if a beginner is typing slowly but learning the code structure, will the game support that player with easier settings, slower enemies, or hints, or is the main goal to challenge players under pressure?

## Suggestion: A practical next step or idea they could implement
A practical next step would be to make the checklist that includes the main features needed before submission: confirm the boss loop works, confirm upgrades actually affect gameplay, test the end-of-run stats screen, and clean up the README status.
